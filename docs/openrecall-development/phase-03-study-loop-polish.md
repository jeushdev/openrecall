# Phase 03 — Study-loop polish

Planning only; no source changes. Four independently implementable milestones. Findings below come from current study/session/settings code and direct dependencies, without prior milestone or Git-history reconstruction.

Paths below are repository-relative. Preserve queue selection, requeue placement, mastery thresholds, park rules, answer matching, existing design tokens, and responsive layout. No completion-screen redesign, spaced repetition, AI, analytics dashboards, new modes, offline architecture changes, session-engine rewrite, or general UI redesign.

## 1. Returning-card indicator

- **Objective:** Distinguish a first appearance from a retry caused by a below-Mastered result in this session.
- **Current findings:** `StudySessionState.applyResult` removes mastered cards and requeues every lower result. `StudyQueueItem.consecutiveFails` is session-scoped but resets in `declinePark`; global `FlashCard.failCount` includes other sessions. Neither alone reliably identifies retries. `SessionController.start` resumes an existing live session in memory; new sessions/drills seed fresh queues. The screen keys attempts by session-card ID and queue position, including immediate single-card retries.
- **Files/classes:** `lib/features/study/domain/study_queue_item.dart` (`StudyQueueItem`); `domain/study_session_state.dart` (`StudySessionState`); `application/session_controller.dart` (under the same study feature); `presentation/study_session_screen.dart` (`_ActiveBody`).
- **Minimal approach / state:** Add session-local `requeueCount = 0` to each queue item; increment only in the actual failure/requeue branch, preserve through copies and park-decline, and include in equality/hash. Expose `CardAppearance { firstAttempt, returning }` derived from that count through a small current-card getter. Do not derive it from lifetime failures, position magnitude, or widget rebuilds. Render a subdued text/icon `Returning card` label near the current card, only while studying.
- **Lifecycle / edge cases:** Same-session navigation retains the count; a new session or parked drill starts at zero. A one-card failure immediately becomes returning. Third-failure park prompts must not mislabel the next queued card; decline keeps retry history even when consecutive failures reset. No label for an absent/completed current card. No database fields: current resume is in-memory, not process-restart restoration.
- **Targeted tests:** Extend `test/features/study/study_session_state_test.dart` for historical failures on first appearance, requeue, single-card repeat, park-decline, and fresh seed. Extend `session_controller_test.dart` for resume/new drill; `study_session_screen_test.dart` for label visibility and narrow layout.
- **Acceptance:** Every actual same-session retry is labeled, every fresh appearance is unlabeled, and existing mastery/requeue/park tests remain unchanged in behavior.
- **Non-goals:** Changing fail counters, scheduling, mastery, or persistent resume. No dependency on other milestones.

## 2. Cloze letter-by-letter hints

- **Objective:** Reveal progressively more of the active blank while retaining whether recall was assisted.
- **Current findings:** `ClozeTypeCard` builds answers from exact front/back keyword occurrences, advances one blank at a time, and stores all attempt details locally. A miss shows the answer/diff plus override/Next. `_derive` emits correct, overridden, or missed once; `ClozeOutcome` maps these to existing mastery levels. Re-keying by session-card ID/position resets retries. `StudyRepository` currently has no attempt-record API.
- **Files/classes:** `lib/features/study/presentation/widgets/cloze_type_card.dart`; `presentation/study_session_screen.dart`; `application/session_controller.dart`; `domain/study_session_state.dart`; new `domain/cloze_hint.dart` and small typed attempt-metadata model. `domain/cloze_blank.dart` and `domain/cloze_outcome.dart` are behavioral references; preserve their parsing/evaluation. Add an explicit grapheme dependency in `pubspec.yaml` if needed.
- **Minimal approach:** Place a small `Hint` action and wrapping answer preview beside the existing input controls. Each press reveals the next hidden user-perceived character in reading order for the active blank only. Keep the typed input untouched; revealing the full answer does not submit or advance. Disable hints during miss review, after emission, and when nothing remains to reveal.
- **Whitespace / punctuation:** On first hint, show whitespace and punctuation literally in a masked preview without consuming a press; reveal one remaining grapheme on that same press. Letters, digits, and other non-separator symbols consume one press each. Preserve casing, accents, repeated spaces, and multi-word boundaries; never slice UTF-16 code units. Example: `New York` progresses `N•• ••••`, `Ne• ••••`, then onward. A punctuation-only answer may reveal in one press and still records assistance; zero-blank cards retain existing auto-completion with no hint used.
- **State/data:** Keep per-blank reveal counts widget-local. On the first effective hint, synchronously call an attempt-keyed controller action that records `hintUsed: true` in an immutable session map. Use `(session ID, session-card ID, queue position)` as the attempt key, independently of milestone 1. Record false on an unassisted submission; absence means no recorded attempt activity. Preserve records after mastering, parking, and completion until session reset. Submit via a typed Cloze result carrying the existing outcome plus `hintUsed`; merge with recorded usage using logical OR so an override or widget remount cannot erase assistance. Reject callbacks whose key is no longer the active studying attempt.
- **Reset / storage boundary:** Reset reveal counts on blank advance and on any new attempt, including the same card requeued alone. Retain the attempt-level flag across blanks and route exit/resume, even if local reveal progress resets on remount. Fresh attempts start unassisted while older records remain. This phase stores metadata in live session state only, explicitly not durably across app restarts; future analytics can consume this typed boundary without inferring assistance from outcomes. No schema/sync work is required.
- **Targeted tests:** New helper tests for repeated presses, cap, punctuation, multiple words, digits, and composed Unicode. Extend `cloze_type_card_test.dart` for active-blank isolation, unchanged input, full reveal without submission, review disablement, override retention, no-blank behavior, and one emission. Extend state/controller/screen tests for assisted/unassisted submissions, immediate retry reset, stale callbacks, and assistance retained after completion/navigation.
- **Acceptance:** Each effective press reveals the specified next character; matching and outcome-to-mastery mappings remain identical. Hint usage reaches session state before submission and survives card removal. Existing Cloze matching/outcome tests still pass.
- **Non-goals:** Cloze redesign, hint penalties, automatic answer insertion, mastery or first-try metric redefinition, durable attempt history, analytics UI. No dependency on milestones 1, 3, or 4.

## 3. Optional study sounds

- **Objective:** Provide opt-in, centralized sound for meaningful study events.
- **Current findings:** Settings uses injectable SharedPreferences stores and Riverpod AsyncNotifier controllers with optimistic updates/rollback. `SettingsTabScreen` already has `_ToggleRow`. Study interactions currently invoke haptics in `_ActiveBody`; `pubspec.yaml` declares no audio playback package or sound assets. Result application and park confirmation are the two completion paths.
- **Files/classes:** New `lib/features/settings/data/study_sound_preferences.dart`; existing `application/settings_providers.dart` and `lib/ui/settings/settings_tab_screen.dart`; new study `application/study_feedback_service.dart` with injectable audio adapter under `data/`; `application/session_controller.dart`; `pubspec.yaml` and two short bundled assets under `assets/sounds/`.
- **Minimal approach / state:** Add a device-local `study_sounds_enabled` boolean, default false; follow existing preference-store/provider patterns with read-failure fallback and write rollback. Reuse `_ToggleRow` in a small Study feedback settings section available on web and native. Serialize preference writes (or disable the toggle while saving) to avoid rapid-toggle persistence races. Treat unsuccessful storage writes as failures.
- **Event ownership:** The controller invokes one typed feedback service after accepted synchronous transitions: `cardMastered` when a result retires a card, and `sessionCompleted` on a transition to completed from result application or park confirmation. Pass a session-scoped transition identity for deduplication. Completion wins over mastery when the last card causes both: play one completion cue. No sound on seed/reattach, background write retry, ordinary rating/tap, hint, requeue, or exit. Do not trigger playback from build methods or individual study widgets.
- **Playback policy / edge cases:** Gate against the current loaded preference; remain silent while loading or on errors, without replaying missed events when enabled. Use a small asset-backed cross-platform adapter chosen/verified during implementation; do not prescribe an unverified package version here. Playback is best-effort, nonblocking, and non-overlapping; cancel pending cues when disabled and dispose player resources. Browser user-gesture restrictions, unavailable devices, and asset failures degrade silently. Existing haptics remain independent.
- **Targeted tests:** New preference/provider tests for default, persistence across provider recreation, fallback, rollback, and rapid toggles; extend `test/ui/settings/settings_tab_screen_test.dart`. Fake the audio adapter in controller/service tests: one mastery cue, one completion cue including final park, final-card precedence, disabled/loading silence, no duplicate on reattach/rebuild/write retries, and nonblocking failure. Smoke-test bundled playback on supported native/web targets.
- **Acceptance:** Settings reliably persists the toggle locally; only accepted mastery/completion transitions produce at most one cue, and study progress never waits for audio.
- **Non-goals:** Per-tap audio, sound packs, volume controls, notification changes, remote assets, or widget-level player calls. Implementable without returning/hint/visual-polish work.

## 4. Study feedback polish

- **Objective:** Make outcomes and the next attempt clear within the existing study screen.
- **Current findings:** `_ActiveBody` already uses directional slide/fade transitions (220 ms), haptics, a resolved/total counter, and a scrollable constrained card area. Results advance synchronously. Cloze has explicit miss review, while ordinary ratings primarily communicate through motion; there are no typed returning/hint labels yet.
- **Files/classes:** `lib/features/study/presentation/study_session_screen.dart`; small new `presentation/widgets/study_feedback_status.dart`; `presentation/widgets/cloze_type_card.dart`; `domain/study_session_state.dart` and `application/session_controller.dart` for a minimal last-result notice. Reuse existing `AppTokens`, `AppType`, layout, and progress components.
- **Minimal approach / state:** Record a small immutable last-result notice with a monotonic revision, source attempt key, and mastered/requeued/park-prompt verdict from accepted state transitions. Present it in a reserved, wrapping status area near the card: `Previous card mastered` or `Previous card will return`; for an immediate same-card retry use `Try this card again`. A park prompt takes precedence over ordinary requeue feedback. Keep current-card status separate: `Returning card` and `Hint used` identify the active attempt rather than the previous result. An assisted mastered result can read `Previous card mastered · Hint used` without implying unassisted recall.
- **Transition behavior:** Preserve immediate engine advancement and existing 220 ms motion; do not add waits or an extra Next action. Keep the last-result notice readable until the next accepted result, separate from current badges, and clear it on new session. Scope notices to session/attempt identities so navigation does not reannounce old events. Disable pointer/semantics interaction on outgoing AnimatedSwitcher children; reject duplicate/stale attempt submissions so rapid taps cannot rate the incoming card. Respect reduced-motion settings and announce each new result once via semantics, using text as well as color. Terminal outcomes use the existing completion view and an announcement, without redesigning it or delaying arrival.
- **Independent delivery:** Base feedback uses existing `RatingEffects` and phases. Give the status widget optional typed returning/assistance inputs with neutral defaults; wire milestone 1/2 inputs when available. Do not duplicate retry inference or hint storage here. Visual notices and milestone 3 audio can consume the same accepted transition identities, but neither requires the other to ship.
- **Edge cases:** Single-card retries; third-fail modal and decline/confirm; assisted override; last-card completion; fast input during animation; route exit/resume; keyboard-open small screens; long strings and maximum card/system text scale. Preserve scrollability, safe areas, rating gates, and light/dark token contrast.
- **Targeted tests:** Extend `study_session_screen_test.dart` for verdict copy, previous-versus-current attribution, prompt precedence, final transition, duplicate input, one semantics announcement, and optional badge inputs. Add focused status-widget tests for narrow widths, large text, and light/dark themes; verify reduced-motion behavior. Retain existing Flip reveal/swipe, Cloze, and Feynman rating-gate tests.
- **Acceptance:** Mastery, requeue, returning status, and assistance are distinguishable without relying on motion/color alone; next-card progression remains immediate, exactly once per attempt, responsive, and visually consistent.
- **Non-goals:** Completion-screen redesign, new controls in the core loop, global animation changes, mastery changes, or broader UI cleanup.

## Delivery boundary

Shared-file overlap is integration work, not a prerequisite to starting another milestone. Defaults are sounds off, hints do not alter evaluation, and assistance metadata is retained for the live session only. No unresolved product decision blocks this plan.
